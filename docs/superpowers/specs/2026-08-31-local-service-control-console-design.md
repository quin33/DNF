# 本机服务控制台设计规格

## 1. 背景与目标

当前项目由单个 `server.js` 进程同时提供网页静态资源、HTTP API、WebSocket、SQLite 和远程 AI 调用。现有启动脚本可以启动服务，但无法可靠地查看状态、切换 AI、重启网页服务或保留重启过程中的控制入口。

本功能增加一个仅绑定本机回环地址的独立控制器与可视化控制台，用于：

- 查看网页服务器和 AI 接口的实时状态。
- 启动、停止、重启网页服务器子进程。
- 启用或停用远程 AI 调用。
- 重载 AI 配置并执行健康检查。
- 查看最近运行日志、错误和操作记录。

## 2. 范围

### 包含

- Windows 本机运行。
- 控制器独立监听 `127.0.0.1:8790`。
- 游戏服务器继续监听 `127.0.0.1:8787` 或现有 `PORT` 配置。
- 控制器作为父进程管理 `server.js` 子进程。
- AI 作为远程接口的运行时开关，而非独立进程。
- 启停、重启、配置重载、健康检查、日志查看。

### 不包含

- 公网或局域网远程控制。
- 任意 Shell 命令执行。
- 控制 Cloudflare Tunnel、数据库备份或操作系统服务。
- 修改 AI 提供商的远程账户或密钥。
- 在控制台展示完整 API Key。

## 3. 方案选择

### 方案 A：独立 Node 控制器（采用）

控制器单独运行，负责创建和监控 `server.js` 子进程。控制台不会因游戏服务器重启而消失，适合长期使用和后续扩展。

### 方案 B：扩展现有管理后台

实现量较小，但管理后台与 `server.js` 生命周期绑定，无法可靠控制自身重启，启动失败时也没有独立恢复入口。不采用。

### 方案 C：PowerShell 脚本配静态页面

Windows 进程控制方便，但状态、日志、鉴权和后续 UI 扩展会分散在多个运行时。不采用。

## 4. 总体架构

```text
control-panel.js
  ├─ HTTP API + 静态控制台
  ├─ service-supervisor.js
  │    ├─ spawn/stop/restart server.js
  │    ├─ 进程状态与端口检查
  │    └─ 子进程 stdout/stderr 日志
  ├─ runtime-state.json
  │    └─ AI 开关、最近操作、启动策略
  └─ server.js 子进程
       ├─ 游戏网页与 API
       ├─ WebSocket
       ├─ SQLite
       └─ 远程 AI 接口
```

控制器只绑定 `127.0.0.1`，不暴露到局域网或公网。游戏服务器的启动环境继承当前 `.env` 与控制器配置，但密钥不进入浏览器和控制器响应。

控制器启动 `server.js` 时为子进程保留 Node IPC 通道（`stdio` 中包含 `ipc`）。控制器通过该通道发送运行时配置变更，`server.js` 在内存中更新 AI 运行状态并回传确认；配置重载或进程重启后再从状态文件和环境变量恢复。这样 AI 开关不依赖重启才能生效。

若控制器启动时发现 `8787` 已有一个健康但非本控制器创建的进程，则标记为“已发现、未接管”：可以读取状态和打开游戏，但不能假设它支持 IPC。此时 AI 开关和配置重载操作必须先提示用户重启并接管该进程，避免控制台显示的开关状态与实际业务状态不一致。

## 5. 进程生命周期

### 启动

1. 控制器加载 `runtime-state.json` 和 `.env`。
2. 检查 `8787` 是否已有健康的游戏服务器。
3. 若无，则以 `node server.js` 启动子进程。
4. 等待端口监听和 `/api/health` 返回成功。
5. 向控制台广播 `running` 状态。

### 重启

1. 控制台要求二次确认并生成操作编号。
2. 状态变更为 `restarting`，暂时拒绝重复重启。
3. 向子进程发送结束信号；必要时使用 Windows 进程树终止兜底。
4. 等待端口释放，超时则记录错误并停止自动重试。
5. 使用最新环境变量重新启动 `server.js`。
6. 轮询 `/api/health`，成功后回到 `running`。
7. 失败则进入 `error`，控制器仍保持可访问。

默认不做无限自动重启；可配置最多 2 次、间隔 3 秒的启动重试。

### 异常退出

控制器监听子进程 `exit` 事件，记录退出码和 stderr 摘要。默认只标记为 `crashed`，不自动循环拉起；控制台提供明确的“重新启动”操作。

## 6. AI 运行时开关

AI 不单独创建或终止进程。控制台的“AI 重启”定义为“重载配置并重置连接状态”：

1. 读取 `.env` 中的 `AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL` 等配置。
2. 读取 `AI_ENABLED` 运行时覆盖值。
3. 清理最近一次 AI 错误和健康检查结果。
4. 调用一次不产生游戏副作用的连接检查。
5. 广播新的 AI 状态。

运行时状态优先级固定为：控制器状态文件覆盖值 > `.env` 中的 `AI_ENABLED` > 默认值 `true`。控制器发送 IPC 配置时，服务端必须返回已应用的版本号；若未收到确认，控制台将操作标记为失败，不显示“已生效”。

停用时，`server.js` 不向远程 AI 发送请求，并返回明确的 `ai_disabled` 错误。是否使用本地备用叙事由现有业务逻辑决定，不在控制器中复制游戏规则。默认采用严格停用模式，避免玩家误以为 AI 正常工作。

AI 状态至少包含：

```json
{
  "enabled": true,
  "configured": true,
  "reachable": true,
  "model": "deepseek-chat",
  "lastCheckedAt": 0,
  "lastError": ""
}
```

## 7. 控制台界面

控制台采用紧凑的运维面板，不做营销式首页。

### 顶部

- 控制器在线状态。
- 当前时间。
- 游戏服务端口和 PID。
- 最近一次操作结果。

### 网页服务器卡片

- 状态：运行中、已停止、启动中、重启中、异常退出。
- PID、端口、启动时间、健康检查时间。
- 启动、停止、重启按钮。
- 打开游戏页面按钮。
- 查看日志按钮。

### AI 服务卡片

- 启用/停用开关。
- 配置状态、可达状态、模型名。
- 最近检查时间和错误摘要。
- 重载配置、测试连接按钮。

### 日志区

- 默认显示最近 100 条，内存最多保留 500 条。
- 按服务、级别和时间筛选。
- 自动隐藏 API Key、Bearer Token 和密码字段。
- 支持复制摘要和下载脱敏日志。

所有危险按钮使用图标加文字、明确的悬浮提示和二次确认。重启期间按钮固定尺寸并显示进行中状态，避免重复点击造成多个子进程。

## 8. 控制器 API

控制器 API 只接受本机请求，并要求管理员令牌。

```text
GET  /api/control/health
GET  /api/control/status
GET  /api/control/logs?service=all&level=all
POST /api/control/server/start
POST /api/control/server/stop
POST /api/control/server/restart
POST /api/control/ai/toggle       { enabled: boolean }
POST /api/control/ai/reload
POST /api/control/ai/check
```

统一响应包含：

```json
{
  "ok": true,
  "operationId": "op-...",
  "status": "running",
  "message": "",
  "updatedAt": 0
}
```

控制器不提供任意命令、任意路径或任意环境变量写入接口。

## 9. 状态与并发规则

- 每项服务只有一个生命周期操作可以处于执行中。
- 相同操作重复提交返回 `409 operation_in_progress`。
- 状态变化通过短轮询或 Server-Sent Events 推送到控制台。
- 控制器重启后从实际 PID、端口和健康检查重新推导状态，不盲信状态文件。
- `runtime-state.json` 只保存 AI 开关和最近操作元数据，不保存密钥。
- 控制器与子进程之间的 IPC 消息带单调递增版本号，旧消息不得覆盖新配置。
- 未被控制器创建的外部进程不支持无重启热切换，必须先接管。

## 10. 安全边界

- 控制器绑定 `127.0.0.1`。
- 首次启动要求设置独立控制台密码；密码只保存哈希。
- 使用 HttpOnly 会话 Cookie 或短期 Bearer Token。
- 所有 POST 操作校验 Origin、会话和 CSRF 令牌。
- 重启、停用 AI、停止服务必须二次确认。
- 日志脱敏后再返回前端。
- 控制器进程不向游戏页面注入管理凭据。

## 11. 失败处理

- 端口被占用：显示占用状态和 PID，不自动杀死未知进程。
- 启动失败：读取 stderr 最后 50 行，保留控制台可用。
- 健康检查超时：区分“进程已启动但服务未就绪”和“进程已退出”。
- 停止超时：先记录告警，再执行进程树终止；仍失败则显示人工处理提示。
- AI 检查失败：保持服务开关状态不变，只更新 `reachable=false` 和错误信息。
- 控制器自身异常：不执行破坏性自动操作，避免误杀游戏服务。

## 12. 测试与验收

### 单元测试

- 状态机转换合法性。
- 重启操作幂等和重复点击保护。
- 端口/健康检查结果解析。
- AI 开关读写与配置脱敏。
- Windows 子进程退出码处理。

### 集成测试

- 控制器启动游戏服务器并确认 `/api/health`。
- 重启游戏服务器时控制台仍能访问。
- 游戏服务器启动失败后控制台显示错误。
- AI 停用后请求不会触发远程调用。
- AI 重载后模型和配置状态更新。
- 未授权、本机外地址和伪造操作请求被拒绝。

### 手工验收

1. 打开 `http://127.0.0.1:8790`。
2. 查看游戏服务运行状态和 PID。
3. 点击重启，确认游戏服务短暂不可用但控制台不中断。
4. 停用 AI，确认状态变为已停用且游戏端得到明确提示。
5. 重载配置并测试连接，确认状态恢复。

## 13. 交付顺序

1. `service-supervisor.js`：进程状态机和 Windows 进程控制。
2. `control-panel.js`：本机鉴权、控制器 API、日志和状态广播。
3. `control-panel.html` 与配套 CSS/JS：可视化控制台。
4. 修改 `server.js`：接入 `AI_ENABLED` 运行时状态和受控配置重载。
5. 增加启动脚本：优先启动控制器，由控制器启动游戏服务。
6. 补充单元、集成和手工验收测试。
