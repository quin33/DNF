# AI 驱动副本流程设计

**日期：** 2026-08-26

## 背景

当前副本在开始时预先生成探索、战斗、首领、搜刮、归途等阶段及各自步数。每一步只消费当前阶段的一个计数，计数耗尽后进入下一阶段；全部计数耗尽后直接结算。

这种方式可以保证流程完整，但无法保证剧情完整。若 AI 在首领阶段刚提出新的敌人、谜团或任务目标，下一阶段仍可能按计划切换到搜刮或归途，导致故事在冲突尚未解决时结束。日志 #69175 即属于这种情况。

## 目标

1. 不再在副本开始时预先分配探索、战斗、首领、搜刮和归途的步数。
2. 每一步由 AI 根据当前上下文决定下一步的叙事方向和事件推进。
3. 任务目标、首领冲突和撤退结果必须在剧情上得到解决后，才允许进入归途和结算。
4. 保留引擎的最小步数、最大步数、角色焦点和结算安全边界。
5. 联机模式与单机模式使用同一套阶段决策语义，避免两套流程继续漂移。

## 非目标

1. 不要求 AI 永远遵守角色出场、字数或文风提示；本次不增加违规检测与自动重试。
2. 不在本次改动中重写完整叙事生成器或替换现有角色高光系统。
3. 不改变已有日志、结算、战利品和角色成长的业务规则。

## 推荐架构

采用“AI 决策、引擎约束”的混合状态机，而不是把流程控制完全交给 AI。

每一步的流程为：

```text
读取副本状态与最近上下文
    -> AI 返回本步正文 + 下一叙事方向 + 任务进展/冲突解决状态
    -> 引擎规范化并应用状态变化
    -> 引擎判断是否允许继续、进入归途或结算
    -> 若继续，下一步再次请求 AI
```

AI 可以选择的方向包括：`explore`、`encounter`、`battle`、`boss`、`loot`、`rest`、`retreat`、`closing`。`opening` 仍由引擎作为第一步固定提示，`closing` 只能由引擎在满足收束条件后开放。

## 副本状态

副本状态从“预先生成的 `plan`”转为“当前状态 + 历史事件”。建议新增或统一以下字段：

```js
{
  minSteps: 10,
  maxSteps: 40,
  totalStep: 0,
  phase: 'opening',
  quest: {
    objective: '取回雷池真宝',
    status: 'active', // active | completed | failed | retreated
  },
  encounter: {
    active: false,
    kind: null,       // battle | boss | hazard
    name: null,
    status: 'none',   // none | active | resolved | escaped
  },
  lastDecision: null,
  steps: []
}
```

原有 `focusPlan` 保留，但不再依赖阶段步数总和生成。焦点窗口应根据实际生成的步数动态追加；开局和归途仍为群像，普通事件继续使用 2~3 步连续焦点。

## AI 响应契约

AI 每步返回一个 JSON 对象，正文和控制信息放在同一响应中：

```json
{
  "text": "本步叙事正文",
  "phase": "boss",
  "event": "advance",
  "questStatus": "active",
  "encounterStatus": "active",
  "nextHint": "继续寻找雷池真宝",
  "continue": true
}
```

字段语义：

- `text`：本步正文，继续受现有单步长度限制。
- `phase`：AI 建议的下一叙事方向。
- `event`：本步结果，至少支持 `advance`、`resolve`、`fail`、`retreat`。
- `questStatus`：任务是否完成、失败或仍在进行。
- `encounterStatus`：当前战斗/首领/危险是否仍在持续。
- `nextHint`：给下一步 AI 的简短连续性提示。
- `continue`：是否请求下一步；最终是否真的结束由引擎再次判定。

如果 AI 返回的控制字段缺失或不合法，引擎保留正文，将 `phase` 归一化为当前阶段，按 `questStatus=active`、`encounterStatus=active` 处理，不直接结算。

## 引擎安全边界

### 最小步数

- `totalStep < minSteps` 时，AI 不得结束副本。
- 即使 AI 返回 `continue=false` 或 `phase=closing`，引擎也要求继续生成下一步。

### 最大步数

- `totalStep >= maxSteps` 时必须结束本局。
- 若任务仍未完成，结局统一转为明确的失败或撤退，不得伪造成功复命。

### 归途开放条件

- 只有满足以下任一条件时，才允许 `closing`：
  - `quest.status === 'completed'`；
  - `quest.status === 'failed'`；
  - `quest.status === 'retreated'`。
- `encounter.status === 'active'` 时禁止进入归途。
- AI 在最后一步不得开启新的首领、核心谜团或需要后续解释的任务目标。

### 阶段决策规范化

- `phase=loot` 只能在当前事件已经取得安全窗口或冲突已解决时采用。
- `phase=boss` 可以连续多步保持，直到首领状态变为 `resolved` 或 `escaped`。
- `phase=retreat` 必须明确撤退成功或失败；撤退成功自动将任务标记为 `retreated`，按失败结算。
- `phase=closing` 由引擎转换为 `closing`，不再接受 AI 临时开启的新冲突。

## 提示词调整

系统提示词不再把阶段描述为固定顺序，也不再暗示每个阶段有预定步数。新增以下要求：

1. 每一步都要根据当前任务状态决定下一事件，不必轮流经过所有阶段。
2. 若当前冲突、首领或任务目标尚未解决，必须继续处理，不能切换到搜刮或归途。
3. 只有在任务完成、失败或明确撤退后才能收尾。
4. 最后两步不得引入新的未闭合主线。
5. 正文之外输出结构化控制字段，字段只描述本步已经发生或明确决定的状态，不得预告未发生的结果。

角色允许出场名单、禁止主动出场名单和连续焦点规则继续保留。

## 联机与单机数据流

### 联机模式

- `server.js` 负责保存权威副本状态、调用 AI、规范化 AI 决策、判断是否继续以及最终结算。
- WebSocket 的 `step` 消息增加规范化后的 `phase`、`questStatus`、`encounterStatus`，客户端只展示，不自行决定结算。

### 单机模式

- `index.html` 复用同样的决策字段和安全边界。
- 单机 AI 请求与联机请求使用同一套提示词结构。
- 本地降级叙事只负责生成正文，若无法生成控制字段，则沿用当前阶段并继续，不得绕过最小/最大步数边界。

### 兼容旧存档

- 已完成日志无需迁移。
- 仍在进行中的旧快照若含 `plan`，恢复时继续按旧计划跑完；新建副本使用 AI 驱动状态机。
- 旧快照缺少新状态字段时，根据已有 `steps` 和当前 `planIdx/stepIdx` 推导 `phase`，任务状态默认为 `active`，避免恢复时突然结算。

## 错误处理

1. AI 网络失败、空响应或无法解析正文时，沿用现有失败处理，不保存伪造的完成日志。
2. AI 正文有效但控制字段无效时，只降级控制字段，不丢弃正文，也不自动重试。
3. 结算调用失败时，保留现有 `failed` 处理，不能把未完成剧情标记为成功。
4. 达到最大步数仍未闭合时，结局必须写明任务失败或被迫撤退，并将原因传给结算摘要。

## 测试范围

### 单元测试

1. 新副本不再创建按阶段预分配的步数表。
2. AI 可以连续返回同一阶段，阶段不会被计数器强制切换。
3. 未解决首领冲突时，`closing` 被引擎拒绝。
4. 任务完成、失败、撤退三种状态都能合法进入归途。
5. 最小步数和最大步数边界生效。
6. 无效控制字段不会导致提前结算。
7. 动态步数下焦点窗口仍保持 2~3 步，并且每名角色有高光机会。

### 集成测试

1. 模拟“先提出更深层首领，再继续两步，最后解决”的流程，确认不会在悬念提出后直接搜刮或归途。
2. 模拟最大步数仍未完成，确认日志状态为失败而非成功。
3. 联机与单机对同一决策序列得到一致的阶段和结算条件。
4. 旧计划快照恢复不受影响。
